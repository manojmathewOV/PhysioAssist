## P08 (G01): clean test exits: root cause and fix

**Root causes (both confirmed):**

1. **Importing the store started persistence.** `src/store/index.ts` created the live store and called `persistStore` when the module was imported. redux-persist then scheduled its 5 s rehydration timeout. Every test that imported `rootReducer` from the store therefore held a timer.
2. **The telemetry singleton started a 5 s `setInterval` in its constructor that never stopped.** It is imported by `deviceHealthMonitor` and the video-comparison services.
   - At 414b81b, `jest --ci --detectOpenHandles` reported 6 open handles from `telemetryService.ts:91` and did not finish within 580 s (exit 124).

**Fixes:**

- The live store moved to `src/store/appStore.ts`, imported only by App. `store/index.ts` now holds reducers and types.
- The telemetry flush is a one-shot timer, scheduled only while events are queued. An idle app no longer has a timer waking it every 5 s.
- One shared teardown in `__tests__/setup.ts`, so queued telemetry is not sent after a test file finishes.
- No `--forceExit`, no timeout changes, and no `.unref()`.

**Data-safety finding found on the way (G02):** redux-persist's default timeout (5 s) gives up on a slow storage read, marks the state as rehydrated with the empty initial state, and then saves that over the stored data. On iOS, a Keychain read that is slow (for example on a locked phone) could therefore erase the patient's history.

- Rehydration now waits for storage (`timeout: 0`).
- `persistence.test.ts` covers this. With the old 5 s value the test fails: `setItem` is called twice before the stored read arrives. With the fix it passes, and the saved history is restored.
- **Still open for G02:** a storage *read error* still rehydrates the empty state. This path is unchanged; the transactional storage work (G02) must handle it visibly.
